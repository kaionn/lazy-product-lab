## 1. 下書き迷子防止くん

- カテゴリ: Browser Extension
- 対象ユーザー: 社内申請フォームや問い合わせフォームなど自動保存のないtextareaに長文を書く人
- 一行で: textareaに文字を打つだけでブラウザが落ちても消えても自動で下書きが復元されるのだ

### 解決する痛み

数百字書いた申請フォームや問い合わせフォームで、うっかり戻るボタンを押したりタブを閉じたりして全文が消える。社内の古いシステムほど自動保存機能がなく、書き終えた瞬間にセッション切れやネットワークエラーで送信失敗すると全部書き直しになる。コピペで別テキストにバックアップする習慣をつけようとしても、忙しいときほど忘れて涙を飲む。

### 1 週間で作るならこれ

- 拡張機能が全ページのtextarea/contenteditableを監視し、入力のたびにchrome.storage.localへ自動保存（3秒デバウンス）
- 同じURLのページを再訪したときに「保存された下書きがあります」バナーを表示し、ワンクリックで復元
- 保存済み下書きの一覧をポップアップから確認・削除できる
- 保存データは7日で自動削除して無限に溜まらないようにする
- type="password"を含むフォームは監視対象から除外する

### なぜ雑か

同一URLに複数の下書きがある場合は最新1件で上書き（バージョン管理なし）。URLが変わらないSPA内のフォーム切り替えは誤爆・見逃しがある。iframe内のフォームは対象外。文字数制限などフォーム側の制約チェックはせずそのまま保存するだけ。

### 雑な技術スタック候補

Chrome Extension (Manifest V3) + MutationObserver + chrome.storage.local + 素のJavaScript（フレームワークなし）

## 2. 退職者アカウント置き去り検知

- カテゴリ: 業務ツール (Web)
- 対象ユーザー: 数十〜数百人規模の会社でSaaSアカウントの退職者対応をしている情シス・バックオフィス担当
- 一行で: 退職者リストをアップロードするだけで残ってる各種SaaSアカウントを突き合わせて教えてくれるのだ

### 解決する痛み

退職者が出るたびにGoogle Workspace、Slack、GitHubなど契約中のSaaSをひとつひとつ手動で無効化しているが、繁忙期や担当交代のタイミングで漏れが発生する。半年後に「辞めた人がまだSlackに入ってる」と気づいて青ざめる。情報漏洩リスクに直結するのに、四半期ごとの棚卸しは表計算とにらめっこするだけの苦行で誰もやりたがらない。

### 1 週間で作るならこれ

- 退職者リスト（氏名・メールアドレス・退職日）をCSVでアップロード
- Google Workspace Admin SDK / Slack SCIM API / GitHub Org Members APIから現在アクティブなユーザー一覧を取得（対応は3サービス限定）
- メールアドレス一致で退職者がまだアクティブなサービスを検出しリスト表示
- 検出結果を週次でSlackに要約通知（「◯件の退職者アカウントが未削除です」）
- 各SaaSの管理画面への直リンクを表示するだけで自動無効化はしない

### なぜ雑か

メールアドレス完全一致でしか照合しないため、退職前にメールアドレスを変更済みだと見逃す。対応SaaSは3つに固定で拡張性は考えない。事故が怖いので自動削除機能は作らず「見つけるだけ」に徹する。APIトークンの権限管理や監査ログなどセキュリティまわりの作り込みは最小限。

### 雑な技術スタック候補

Next.js + Google Admin SDK + Slack SCIM API + Octokit (GitHub API) + Supabase (CSVアップロード保存) + Slack Webhook通知

## 3. でか物コミット狩り

- カテゴリ: CLI
- 対象ユーザー: リポジトリのcloneやpullがいつの間にか遅くなっていることに気づいた開発者
- 一行で: リポジトリを渡すだけで肥大化の原因になった大きいファイルのコミットをランキングしてくれるのだ

### 解決する痛み

誰かが画像やzip、ビルド成果物をうっかりコミットしてしまい、後から`.gitignore`に追加しても履歴には残り続けてclone・pullがどんどん重くなる。「どのコミットが原因か」を`git log`や`du`で手探りするのは時間の無駄だし、BFGやgit-filter-repoで履歴を書き換える決断をする前に、そもそも何が容量を食っているのか誰も把握できていない。犯人が一目でわかれば、履歴を書き換えるかどうかの判断がすぐできる。

### 1 週間で作るならこれ

- `git rev-list --objects --all`と`git cat-file`でリポジトリ内の全オブジェクトサイズを走査
- ファイルサイズでランキングし、削除済みでも履歴に残っていれば対象に含める
- 各ファイルについて最初にコミットされた日時・作者・コミットハッシュを表示
- 合計サイズの上位20件をテーブル出力、`.git`全体に占める割合（%）も表示
- 「このコミットを消せば何MB減るか」の概算値だけ出す（実行はしない）

### なぜ雑か

実際のgit-filter-repoやBFGによる履歴書き換えは行わずレポート出力のみ。Git LFS対象ファイルかどうかの判定はしない。サブモジュールは無視する。巨大リポジトリ（10万コミット超）ではフルスキャンに数分かかる想定でも並列化などの最適化はしない。

### 雑な技術スタック候補

Python + GitPython（もしくは素のgitコマンドをsubprocess） + rich ライブラリでテーブル出力
