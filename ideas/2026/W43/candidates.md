## 1. 空アサーション狩人

- カテゴリ: CLI
- 対象ユーザー: カバレッジ指標だけを見てテストの質を安心材料にしているチームリード・QA担当
- 一行で: テストディレクトリを渡すだけでアサーションが無い/常に真になる「テストもどき」をランキングしてくれるのだ

### 解決する痛み

CIが緑でカバレッジ85%と出ていても、実は`expect(true).toBe(true)`だけで中身を検証していないテストが混ざっていることがある、というのはよくある仮説であり、実際にこの手のテストもどきがチームにとって無視できない量あるかどうかはまだ確認できていない。レビューでロジックまでは読むが「このテスト本当に落ちるの?」までは誰も手を動かして確かめない。リファクタ後にテストが全部通ったのに本番で壊れて初めて「あのテスト、何も検証してなかった」と気づく場面を想定している。

### 1 週間で作るならこれ

- リポジトリパスを渡すとテストファイルをAST解析（ts-morph）してassert/expect文の有無を数える単一のコアフローだけを作る
- assert数が0件、またはassert(true)/expect(true).toBe(true)のような定型の空アサーションパターンを検出
- 検出件数をファイル名・最終更新からの経過日数（git blame）付きでターミナルにランキング表示
- テストもどきを意図的に混ぜ込んだ合成fixtureリポジトリを同梱し、`npx astral-test demo`で30秒以内に「この5件は嘘です」という結果を見せるデモモードを用意
- 対応言語はJS/TS限定（Jest/Vitestの構文のみ）、他言語・他テストフレームワークは対応しない

### なぜ雑か

mutationテストのようにロジックの正しさまでは検証しない。assertの存在チェックのみで、assertが1つでもあれば中身が的を射ているかは問わない。SonarQubeやStrykerのmutation testingは既に近い課題を解いている直接代替であり、本プロダクトはそれらより大幅に軽い「静的パターン検出だけの貧者版」と位置づける。需要があるかどうかは未確認で、npm検索から見つけてもらえるのか、CIテンプレートに直接差し込む形でしか使われないのか、到達可能な配布先はまだ確認できていない課題として残す。

### 雑な技術スタック候補

Node.js + ts-morph（AST解析） + simple-git（blame取得） + commander（CLIパーサ）

## 2. ねこトイレ健診番

- カテゴリ: ガジェット
- 対象ユーザー: 猫の下部尿路疾患（頻尿・血尿）の早期発見をしたい一人暮らし・一匹飼いの猫オーナー
- 一行で: 猫トイレの下に置くだけで入室回数と滞在時間の変化をLINEで教えてくれるのだ

### 解決する痛み

猫の下部尿路疾患は初期症状がトイレの頻度や滞在時間の微妙な変化として出ることがあり、同居していても毎回見ているわけではないので気づきにくい、という仮説に基づいている。実際にオーナーが「いつもと違う」をどの程度見逃しているのか、通知があれば本当に動物病院に行動を移すのかは確認できていない。帰宅して「あれ、今日トイレ何回入ったか覚えてない」という場面を想定し、1匹飼いの家庭に絞って検証したい。

### 1 週間で作るならこれ

- トイレの下にロードセル（重量センサー）を敷いて猫が乗った時だけ重量変化を検知する、という単一のコアフローだけを実装する
- 入室検知から退室までの滞在時間をESP32で計測し、Wi-Fi経由でクラウドにログ送信
- 1日の入室回数・平均滞在時間を直近7日平均と比較し、閾値を超えたらLINE Notifyで通知
- 実機なしでも試せるよう、過去7日分の入室ログCSVサンプルを読み込ませると異常検知結果を30秒で見せるWebダッシュボードのデモモードを用意
- 多頭飼いの個体識別はしない（重量だけでは判別不可なため、1トイレ1匹の家庭限定とする）

### なぜ雑か

個体識別・体重による体調管理・血尿の画像判定などは一切やらない。市販の見守り重量センサー（Catlog Boardなど）は個体識別付きで既に存在する直接代替だが高額であり、本プロダクトはそれより粗くて安い「単一猫・低コスト限定版」という立て付けにする。配布先はLINE個人利用を前提にしており、ペット用品店やSNSの猫コミュニティに実際にリーチできるかどうかは確認していない課題として残す。

### 雑な技術スタック候補

ESP32 + ロードセル(HX711) + LINE Notify API + Firebase Realtime Database

## 3. 英文メール失礼度チェッカー

- カテゴリ: Web (AI ツール)
- 対象ユーザー: 海外クライアントに英語でメールを送る非ネイティブのフリーランス・営業担当
- 一行で: 送る前の英文メールを貼るだけで無意識に失礼・きつく響く表現をハイライトして教えてくれるのだ

### 解決する痛み

非ネイティブが日本語の発想のまま英訳すると、本人には普通でも相手には命令的・ぶっきらぼうに読める表現になりがち、というのはよくある指摘だが、実際にそれで取引やコミュニケーションが悪化している割合は確認できていない仮説にすぎない。締切延長の依頼や請求書の修正依頼のメールを送る前に「これ失礼に見えないか」と一人で不安になるが、聞ける相手が身近にいない場面を想定している。

### 1 週間で作るならこれ

- テキストエリアに英文を貼ると、LLMに「失礼・きつく響く可能性がある箇所」だけを抽出させる単一のコアフローだけを作る
- 該当箇所を本文中でハイライトし、なぜ失礼に響くかの理由とより穏やかな言い換え候補を1つだけ提示
- あらかじめ用意した「きついビジネス英文メール」3パターンをワンクリックで読み込めるサンプルボタンを置き、30秒以内に効果を体感できるデモを用意
- 業界や相手との関係性といった文脈設定は受け付けない（一律の一般的ビジネス英語基準で判定する）
- 言い換え候補はトーン別（カジュアル/フォーマル）に選ばせず常に1つだけ出す

### なぜ雑か

文法チェックや単語選びの細かい添削はしない、失礼度の判定のみに絞る。Grammarlyのトーン検出やChatGPTに直接貼って聞く方法が既に直接代替として存在し、本プロダクトの差分は「失礼ポイントだけに絞った差し込み型UI」という軽さの違いでしかなく、それ自体に需要があるかは未確認。配布先としてProduct HuntやX投稿を想定しているが、実際に非ネイティブの対象ユーザーに届くかどうかは検証していない課題として残す。

### 雑な技術スタック候補

Next.js + OpenAI API (GPT系モデル) + Vercel
