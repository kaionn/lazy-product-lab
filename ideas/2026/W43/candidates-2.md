## 1. 幽霊シークレット検知官

- カテゴリ: CLI
- 対象ユーザー: 複数リポジトリ・複数環境のGitHub Actionsを運用しているインフラ担当・テックリード
- 一行で: ワークフローYAMLを渡すだけで参照されているのに実際には設定されていないsecretsを一覧にしてくれるのだ

### 解決する痛み

workflowで`${{ secrets.FOO_API_KEY }}`と書いたのに、リポジトリ側のSecrets設定にはタイポで`FOO_APIKEY`として登録してしまっていた場合、CIはエラーにならず空文字のまま黙って失敗する、というのはよくある仮説で、実際にこの種の事故がどれだけの頻度で起きているかはまだ確認できていない。新しい環境変数をworkflow側に追加したのにリポジトリのSecrets登録を忘れる、という場面を想定している。CI失敗の原因調査で30分溶かした後にやっと気づく体験を減らしたい。

### 1 週間で作るならこれ

- `.github/workflows/*.yml`をパースして`secrets.XXX`参照を抽出する単一のコアフローだけを作る
- `gh secret list`（GitHub CLI）で実際にリポジトリに登録済みのsecret名一覧を取得し、参照はあるが未登録のものだけを差分表示
- 未登録のsecretをワークフローファイル名・行番号付きでターミナルに一覧表示
- わざと1つ未登録のsecretを参照するworkflowを含んだ合成サンプルリポジトリを同梱し、`npx ghost-secret demo`で30秒以内に検出結果を見せるデモモードを用意
- Environment別secretsやOrganization Secretsの継承関係までは追わず、リポジトリ直下のSecretsのみ対応

### なぜ雑か

secretの値が正しいかどうか（有効期限切れや権限不足）は一切検証しない、存在チェックのみに絞る。既存の`actionlint`はYAML構文やコンテキストの型チェックはしてくれるが、外部のSecrets登録状態とのクロスチェックまでは行わない直接代替であり、本プロダクトはその隙間を狙うが、実際にどれだけのチームがこの事故で困っているのかは未確認の仮説にすぎない。配布先としてGitHub Marketplace ActionやHomebrewを想定しているが、個人のCLIツールとして見つけてもらえるかという到達可能性は確認できていない課題として残す。

### 雑な技術スタック候補

Node.js + js-yaml（ワークフローパース） + GitHub CLI (`gh secret list`) + commander

## 2. 持ち物忘れ番

- カテゴリ: Bot (LINE)
- 対象ユーザー: 小学生以下の子どもの持ち物準備を担当している共働き家庭の親
- 一行で: 曜日ごとの持ち物リストを登録するだけで前の晩にLINEで明日必要なものを教えてくれるのだ

### 解決する痛み

体操着は火曜、絵本袋は木曜のように学校・保育園の持ち物が曜日によって変わり、連絡帳やプリントを見返さないと把握できない、というのはよくある負担だが、実際にどれだけの頻度で親が持ち物を忘れて朝慌てているのかはまだ確認できていない仮説である。朝の支度で時間がない中「あ、今日体操着の日だった」と気づいて慌てる場面を想定している。前の晩のうちに把握できれば朝のバタバタが減るはずという仮説で検証したい。

### 1 週間で作るならこれ

- 曜日×持ち物名のシンプルな表をWebフォームで1回だけ登録する単一のコアフローだけを作る
- 毎晩19時に翌日の曜日に対応する持ち物リストをLINEメッセージとして自動送信するcronジョブ
- 持ち物名はテキスト登録のみ（アイコンや画像設定はしない）
- 「月:体操着, 木:絵本袋」のようなサンプル登録データをワンクリックで読み込めるデモボタンを用意し、登録から通知メッセージ生成までを30秒以内に体感できるようにする
- 持ち物ごとの「用意済みチェック」機能は作らない。通知を送るだけで完結する

### なぜ雑か

複数の子ども・複数の学校/園への対応はしない（1家庭1リストのみ）。長期休みや行事による例外（運動会の弁当など）は反映されない固定の曜日ルーチンのみ対応。家族共有カレンダーアプリのリマインダー機能が既に直接代替として存在するが、それらは持ち物専用の定型フォーマットではなく毎回自分で予定を入力する手間が残るため、本プロダクトは「曜日固定で一度登録すれば終わり」という軽さに絞る。配布先として保護者向けSNSコミュニティや学区の口コミを想定しているが、実際にそこに到達できるかは未検証の課題として残る。

### 雑な技術スタック候補

Next.js（登録フォーム） + Supabase（保存 + pg_cron） + LINE Messaging API

## 3. シューズ寿命番

- カテゴリ: モバイル (PWA)
- 対象ユーザー: ランニングを習慣にしているがシューズの買い替えタイミングがわからないランナー
- 一行で: 走った距離を記録するだけでシューズの寿命が近づいたら買い替えどきを教えてくれるのだ

### 解決する痛み

ランニングシューズは一般的に500〜800km程度で衝撃吸収性能が落ちると言われているが、1足あたりの累計走行距離を正確に覚えているランナーは少なく、気づかないまま劣化したシューズで走り続けている、というのはよくある指摘だが実際にどれだけのランナーがこれで怪我をしているかはまだ確認できていない仮説である。距離は記録していても「このシューズはもう何km走ったか」はシューズ単位で見返す習慣がない場面を想定している。

### 1 週間で作るならこれ

- シューズを登録し、ランニングのたびに距離(km)を手入力して紐づける単一のコアフローだけを作る（外部サービス連携はしない）
- 累計距離をシューズごとに表示し、設定した寿命閾値（デフォルト700km）に対する進捗バーを見せる
- 閾値の80%を超えたらPWAのプッシュ通知で「そろそろ買い替え時」を知らせる
- 3足分・合計距離入力済みのサンプルデータを読み込める「デモを見る」ボタンを用意し、登録から通知までを30秒以内に体感できるようにする
- シューズのモデル別の実際の耐久性データは持たず、閾値はユーザーが手動で設定する固定値のみ対応

### なぜ雑か

外部のランニングアプリとの自動連携はせず、距離は毎回手入力（面倒で続かない可能性を承知の上で雑に割り切る）。シューズの劣化は距離以外にも体重・走り方・路面で変わるが、そうした個人差は一切考慮しない単純な距離カウンターに留める。既存のランニングアプリのシューズ別走行距離集計機能が既に直接代替として存在するため、本プロダクトの差分は「買い替え閾値への接近を能動的に通知する」点に絞るが、それ自体に需要があるかは未確認。配布先としてランニング系SNSやコミュニティでの口コミを想定しているが、到達できるかは検証していない課題として残る。

### 雑な技術スタック候補

Vite + React (PWA) + IndexedDB（ローカル保存） + Web Push API
