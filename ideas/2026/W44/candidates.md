## 1. サンプルコード腐敗検知くん

- カテゴリ: CLI
- 対象ユーザー: READMEや社内Wikiにコード例を載せているOSSメンテナ・ライブラリ作者
- 一行で: READMEを渡すだけでコード例が実際のAPIと合わなくなった箇所を教えてくれるのだ

### 解決する痛み

関数名や引数を変更したときにREADMEのコード例を直すのを忘れ、新しく触る人がそのままコピペしてエラーに詰まる。現状の直接代替は目視レビューか、本格的なdoctest/CIを組む重い対応しかなく、小さなライブラリでは誰もやらない。コード例が動くかどうかは「実際にコピペして試した人が気づいて直す」というギャンブルに依存している。

### 1 週間で作るならこれ

- Markdown内の ```js/```ts コードブロックを正規表現で抽出する単一のコアフローだけを作る
- 抽出したコードを実行し、importエラーや未定義関数の呼び出しを検知
- 呼び出している関数名をASTで抜き出し、実装側のexport一覧と突き合わせて存在しない関数呼び出しを検出
- 壊れている箇所をファイル名・行番号・理由付きでターミナルに一覧表示
- あえて壊したサンプルREADMEを1本仕込んでおき、`npx this-tool README.md` を叩くと30秒以内に赤字で結果が出る「デモを見る」導線を用意する

### なぜ雑か

型チェックはせず「実行できるか」だけを見る。対応言語はJS/TSのみ。複数ファイルに分割されたコード例やシェルコマンド例は対象外。DB接続など外部依存が必要な例はエラーとして握りつぶすだけで誤検知が多く出る想定。これは需要が確認済みの機能ではなく仮説段階で、npm公開後に実際のメンテナが検索で見つけて拾ってくれるか（配布先の到達可能性）は未検証の課題として残す。

### 雑な技術スタック候補

Node.js CLI + remark（Markdownパース） + ts-morph（AST解析） + child_process（サンプル実行） + chalk（出力）

## 2. 自転車タイヤ空気圧番人

- カテゴリ: ガジェット
- 対象ユーザー: 通勤・通学で自転車を使うがタイヤの空気圧チェックをいつも忘れる人
- 一行で: バルブに挟むだけで空気圧が下がったらLINEで教えてくれるのだ

### 解決する痛み

自転車のタイヤは乗らなくても自然に空気が抜けていくが、パンクでもない限り誰も定期的にゲージで測らない。気づかないまま低圧で走り続けてリム打ちパンクや漕ぎ疲れを招く。市販のBluetooth空気圧センサーキャップという直接代替は存在するが、専用アプリを開いて自分から確認しないと気づけない点は変わっておらず、「勝手に教えてくれる」体験にはなっていない。

### 1 週間で作るならこれ

- 既製の圧力センサーモジュールをバルブに固定しESP32に接続する単一のコアフローだけを作る
- 1日1回、決まった時間帯に圧力を測定してWi-Fi経由でサーバーに送信
- 閾値（適正値の80%未満）を下回ったらLINE Messaging APIでメッセージを送信
- 設定画面は作らず閾値はコードに直書きで固定
- 合成的に圧力値を手動で閾値以下に書き換えて送信し、30秒以内にLINE通知が届く様子を確認するデモで価値を見せる

### なぜ雑か

前後輪2箇所分の配線はせず後輪のみ対応。走行中のリアルタイム測定はできず1日1回のポーリングのみ。電池交換の頻度や防水性は未検証でブレッドボードのまま自転車に取り付ける前提。既製Bluetoothセンサーとの価格・精度比較もしておらず、そもそも「勝手に通知」の価値がBluetooth型より本当に高いかは需要確認済みではなく仮説のままにしておく。

### 雑な技術スタック候補

ESP32 + 圧力センサーモジュール + Wi-Fi + LINE Messaging API + Google Apps Script（受け口サーバー代替）

## 3. バグ報告テンプレ忘れ督促くん

- カテゴリ: Bot (Slack)
- 対象ユーザー: 社内バグ報告チャンネルを運用しているエンジニアリングチームのメンバー
- 一行で: バグ報告チャンネルに投稿するだけで再現手順や環境が抜けていたらそっと指摘してくれるのだ

### 解決する痛み

バグ報告用のSlackチャンネルがあっても、投稿者がテンプレートをコピーせず「動きません」の一文だけで終わることが多い。対応する人は再現手順も環境情報もないまま聞き返す往復が発生し、調査が始まるまでに半日かかる。直接の代替は人間が毎回「再現手順教えてください」と手打ちで返信することだが、これも忘れられたり後回しにされて機能していない。

### 1 週間で作るならこれ

- 指定した1チャンネルの新規投稿をSlack Events APIでリッスンする単一のコアフローだけを作る
- 投稿本文に「再現手順」「環境」「期待する動作」のキーワードが含まれているかを単純な文字列マッチで判定
- 含まれていなければスレッドにテンプレート付きで「再現手順と環境を教えてほしい」と自動リプライ
- 誤判定（キーワードはあるが内容が薄い）の精度向上は後回しにする
- テンプレなしの投稿を1件合成的に送り、30秒以内にBotが指摘リプライを返す様子をデモで見せる

### なぜ雑か

キーワードマッチのみでAIによる文章理解はせず、「再現手順」と書いてあれば中身が空でも通過してしまう。対象チャンネルは1つに固定し複数チャンネル対応は後回し。毎回リプライが来ることへの通知疲れ対策も未対応。社内限定利用を前提としており、Slack Appとして外部ワークスペースに配布する場合の権限スコープ審査を通して到達できるかは確認していない課題として残す。

### 雑な技術スタック候補

Slack Bolt (Node.js) + Slack Events API + Railway/Vercel でホスト + 正規表現マッチング
