## 1. 権限盛り過ぎ検知官

- カテゴリ: CLI
- 対象ユーザー: 複数リポジトリでGitHub Actionsワークフローを管理しているSRE・セキュリティ担当
- 一行で: ワークフローYAMLを渡すだけで必要以上に広いpermissionsを付けているジョブを一覧にしてくれるのだ

### 解決する痛み

新人が書いたワークフローに `permissions: write-all` がそのまま残っていたり、実際には `checkout` しかしていないジョブに `contents: write` がついていたりする状況は、レビューで流されがちで誰も気づかない。侵害されたサードパーティactionが混入した場合、権限が広いほど被害範囲が広がるのに、手動でYAMLをgrepして確認するのは面倒で後回しにされる。「このジョブ、本当にこの権限いる?」を機械的に教えてほしい。

### 1 週間で作るならこれ

- `.github/workflows/*.yml` を再帰的にスキャンしてジョブごとの `permissions` ブロックを抽出
- ジョブ内のステップで呼ばれているaction名（`actions/checkout`、`actions/upload-artifact` など主要なもの）から必要そうな最小権限をヒューリスティックで推測
- 現在の権限が推測される最小権限より広いジョブだけをランキングして一覧化
- 「現在の権限 → 推奨される最小権限」を1行で表示
- 結果をターミナル表とMarkdownレポートで出力するだけ（自動修正なし）

### なぜ雑か

推奨権限のヒューリスティックは主要なaction呼び出しパターンのみ対応し、未知のカスタムactionは「判定不能」として素通りする。composite actionやreusable workflow越しに継承される権限は追跡しない。matrix展開やYAMLアンカーを使った複雑な定義は非対応で単純なケースのみ扱う。PRを自動で作る機能はなく、レポートを見て人間が直接YAMLを直す前提。

### 雑な技術スタック候補

Python + PyYAML + Click + 正規表現ベースのaction呼び出し抽出 + rich（テーブル表示）

## 2. レンズ乾燥BOX見張り番

- カテゴリ: ガジェット
- 対象ユーザー: カメラ・レンズを自宅のドライボックスや押し入れで保管している写真好き
- 一行で: ドライボックスに置くだけで湿度がカビの危険域に入ったらLINEで教えてくれるのだ

### 解決する痛み

市販ドライボックスのアナログ湿度計は見に行かないと分からず、乾燥剤切れや蓋の閉め忘れで湿度が上がっても気づくのは何日も後になることが多い。レンズにカビが発生すると清掃費や修理費がかさみ、最悪そのレンズは買い替えになる。旅行や出張で家を空けている間は特にチェックできず、戻ってから後悔するパターンが多い。「湿度がしきい値を超えたらスマホに知らせてほしい」というシンプルな要望に応えたい。

### 1 週間で作るならこれ

- ESP32 + 湿温度センサー（SHT31等）をドライボックス内に設置
- 5分おきに湿度を取得してWi-Fi経由でクラウドに送信
- 湿度がカビ危険域の目安（45%前後）を超えたらLINE Notify/Messaging APIで通知
- 直近24時間の湿度グラフを見れる簡易Webダッシュボード
- しきい値はWeb設定画面から変更可能（1デバイス1ボックスのみ対応）

### なぜ雑か

複数ボックスの同時管理は非対応で1デバイス1ボックス限定。電池駆動ではなくUSB給電前提で配線が蓋からむき出しになる。温度アラートは出さず湿度のみを監視する。通知の再送抑制ロジックはなく、閾値を超えている間は何度も通知が飛ぶ可能性がある。専用ケースは作らず既製ドライボックスの蓋に穴を開けて配線を通すだけ。

### 雑な技術スタック候補

ESP32 + SHT31センサー + Arduino IDE + LINE Notify API + Supabase（時系列データ保存） + Chart.jsの簡易ダッシュボード

## 3. ベンダー障害フィルターくん

- カテゴリ: Bot (Slack)
- 対象ユーザー: 複数の外部API・SaaSに依存するプロダクトを運用しているSRE・バックエンドエンジニア
- 一行で: 使っているサービス名を登録するだけでGitHub/AWS/Datadog等の障害情報から自分たちに関係あるものだけをSlackに教えてくれるのだ

### 解決する痛み

自社が依存する外部サービスのstatus pageは5〜10個あり、全部をRSSやメールで購読すると無関係な障害通知も混ざって埋もれてしまう。障害発生時に気づくのが遅れて「え、GitHub落ちてたの知らなかった」と後から判明することがある。各ベンダーのstatus pageはAtlassian StatuspageやInstatusなど形式がバラバラで、一つの場所でまとめて確認できない。登録したサービスの障害だけを拾って教えてほしい。

### 1 週間で作るならこれ

- 登録フォームで利用中サービスを選択（主要20サービスのstatus page URLを事前登録済み）
- 各サービスのstatus page RSS/JSON APIを5分おきにポーリング
- 新規インシデント検知時にSlack Webhookで「サービス名・影響範囲・開始時刻・status pageリンク」を投稿
- 登録サービス一覧と直近7日間のインシデント履歴を見れる簡易ページ
- 解決済みになったら同じSlackスレッドに「復旧しました」を追記するだけ

### なぜ雑か

事前登録済み20サービス以外は手動でRSS URLを追加する必要があり自動検出はしない。重大度の自動判定はせず全インシデントを同じ扱いで通知する。複数チーム・複数Slackワークスペースへの配信は1アカウント1Webhookのみ対応。過去のインシデント傾向分析やSLA計算のような機能は作らない。

### 雑な技術スタック候補

Node.js + node-cron + Slack Incoming Webhook + 各ベンダーのstatus RSS/Atlassian Statuspage API + Supabase（登録サービス・履歴保存） + 簡易Next.jsページ
