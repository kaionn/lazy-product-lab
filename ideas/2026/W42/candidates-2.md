## 1. ポートコンフリクト検査官

- カテゴリ: CLI
- 対象ユーザー: 複数サービスをdocker-composeでローカル起動しているマイクロサービス開発者
- 一行で: docker-compose.ymlと.envを渡すだけでホストポート番号の衝突を一覧にしてくれるのだ

### 解決する痛み

複数サービスを`docker compose up`で立ち上げると、別チームが追加したサービスが同じホストポートを使っていて「port is already allocated」で止まり、該当ファイルを手でgrepして探す羽目になる。これは実際にどの頻度でチームが困っているか確認済みの需要ではなく仮説であり、今のところの直接代替は起動エラーを読んでcompose/.envファイルを目で探す手作業や、Makefileに手書きしたポート一覧コメントしかない。

### 1 週間で作るならこれ

- docker-compose.yml（複数ファイルのoverride含む）と.env*を再帰的に探索してホストポート番号を抽出する単一コアフロー
- 同一ポートを複数サービスが宣言していたらファイル名・サービス名・行番号付きで一覧表示
- 衝突する2ファイルの合成サンプルを同梱し、`npx portcheck ./fixtures`で30秒以内に衝突検出を見せるデモ導線を用意する
- 衝突なしはexit code 0、衝突ありはexit code 1でCIにも組み込み可能にする
- Kubernetes manifest（containerPort）は今回は対象外、docker-composeのみ

### なぜ雑か

`${PORT:-3000}`のような実行時上書きは追跡せずデフォルト値のみ見る。network_modeがhostでない場合の衝突可能性の違いは無視。npm公開やHomebrew配布はせずGitHubからの直接取得に留めるので、不特定多数の開発者に届ける配布経路は確認課題として残る。

### 雑な技術スタック候補

Node.js + js-yaml + dotenv + 単一スクリプト配布（バイナリ化は見送り）

## 2. 再配達うっかり番人

- カテゴリ: Bot (LINE)
- 対象ユーザー: 宅配の再配達依頼を忘れて荷物を送り主に返送させがちな一人暮らし・在宅勤務者
- 一行で: 配達不在通知メールを転送するだけで再配達依頼の期限が近づくとLINEでせかしてくれるのだ

### 解決する痛み

宅配業者から「ご不在のため持ち帰りました」の通知が来ても、後で依頼しようと思ったまま忘れて保管期限（おおむね1週間）を過ぎ、荷物が送り主へ返送されてしまう。再配達依頼そのものを忘れる人がどれだけいるかは未検証の仮説段階で、直接代替は各運送会社の公式アプリの通知機能だが、ヤマト・佐川・日本郵便をまとめて一箇所で管理する手段は今のところない。

### 1 週間で作るならこれ

- 専用メールアドレスを発行し、不在通知メールをそこに転送するだけで登録完了にする単一コアフロー
- 件名・本文パターンが固定の3社（ヤマト・佐川・日本郵便）分だけ正規表現で運送会社名・問い合わせ番号・保管期限日を抽出
- 保管期限の2日前と前日にLINEで「○○運輸の荷物、期限は◯月◯日です」とリマインド
- 3社分のダミー通知メールで合成デモを用意し、転送してから30秒以内にLINE通知が届く体験を最初に見せる
- 再配達依頼の自動実行はせず、公式サイトへのリンクを貼るだけに留める

### なぜ雑か

3社以外の運送会社や通知メールの書式変更には追従しない。保管期限の計算が1日ずれても補償はしない。個人のLINE Bot運用を想定しており、友だち追加のリンクをどう広げて不特定の利用者に届けるかという配布経路は未検証のまま残る。

### 雑な技術スタック候補

LINE Messaging API + Cloudflare Email Workers（メール受信） + 正規表現パース + Supabase（期限保存） + cron

## 3. スライド時間配分チェッカー

- カテゴリ: Web (AI ツール)
- 対象ユーザー: 社内勉強会やカンファレンス発表前にリハーサルする発表者
- 一行で: 発表の録音を貼るだけでどのスライドに時間を使いすぎたか教えてくれるのだ

### 解決する痛み

発表前のリハーサルで「全体で20分」という総時間は意識しても、どのスライドで想定より話しすぎたのかは本人には分かりにくく、本番で後半だけ早口になりがちだ。スライド単位の時間超過が本番の失敗要因になるという因果はまだ確認されていない仮説であり、直接代替はストップウォッチ片手にスライドを送るたびに手でメモする方法だが、発表の集中を削ってしまう。

### 1 週間で作るならこれ

- リハーサル音声をアップロードし、スライド枚数と各スライドの予定時間を入力する単一コアフロー
- 無音検知で発話区間を区切り、スライド送りのタイミングはユーザーが手動マーカーで打つ（自動のスライド切り替え検知はしない）
- 各スライドの実際の発話時間と予定時間の差分を一覧とグラフで表示
- 3分・5スライドのダミー録音を同梱した合成デモで、アップロードから30秒以内に差分グラフが出る体験を用意する
- 結果はブラウザ内保存のみ（ログインなし、エクスポートはCSVのみ）

### なぜ雑か

画面共有録画やPDF連動によるスライド切り替えの自動検出はせず全部手動マーカー。質疑応答などで話者が混ざると時間がずれても補正しない。まず社内勉強会での試用に留め、個人開発者が不特定のユーザーに届ける配布経路（SNS告知やProduct Huntなど）は確認課題として残す。

### 雑な技術スタック候補

Next.js + Web Audio API（無音検知） + Chart.js + ブラウザ内IndexedDB保存のみ（サーバー不要）
