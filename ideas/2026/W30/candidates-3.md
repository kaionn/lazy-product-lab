## 1. TimeCapsule.md

- カテゴリ: モバイル (PWA)
- 対象ユーザー: 転職・プロダクトローンチ・引越しなど人生の節目を迎えた個人開発者・フリーランサー
- 一行で: 未来の日付まで封印する自分への手紙アプリ

### 解決する痛み
「転職した後の自分へ」「MVP をリリースした 1 年後の自分へ」と書いておきたいメッセージがある。でもノートアプリやメモに書くと次の日に見てしまう。意図的に「指定日まで絶対開けない」仕組みがほしい。タイムカプセル系サービスは複雑で、アカウント登録・メール設定・プラン選択が必要で使い捨て感がない。スマホからサッと書いて 6 ヶ月後に「あの頃の自分はこんなこと考えてたんだ」と読み返すだけでいい。

### 1 週間で作るならこれ
- メッセージ入力フォーム（1000 字以内）と開封解禁日設定（最短 1 ヶ月後から）
- 保存後はコンテンツを blur + Base64 でローカルに保存し、開封日前は内容が見えない UI
- カプセル一覧画面：タイトル・開封日・残り日数のみ表示（中身は非表示）
- 開封日以降にアクセスするとアニメーション演出とともにメッセージが解放
- PWA 化してホーム画面追加可能、ServiceWorker でオフライン対応

### なぜ雑か
暗号化は Base64 に軽い XOR 程度で、localStorage を直接操作すれば開封前でも読める（信頼ベースの設計）。デバイスを変えたらカプセルが消える（クラウド同期なし）。開封日通知は ServiceWorker の Push 通知ではなくアプリを開いた時のチェックのみ。複数カプセルの整合性チェックなし（同じ日付に複数書いても大丈夫）。

### 雑な技術スタック候補
Vite + Preact + Tailwind CSS + localStorage + Workbox (PWA) + Vercel 無料枠

## 2. BreakdownBot

- カテゴリ: その他 (GitHub Actions)
- 対象ユーザー: Issue の書き方が雑なまま作業が始まる一人開発者・小チームのエンジニア
- 一行で: 「○○機能追加」の Issue を開いたら AI が即タスク分解する

### 解決する痛み
「ログイン機能を追加する」みたいな Issue が積み上がっていざ着手すると「で、何から始めるんだっけ」となる。受け入れ基準が書いていないからレビューの基準が曖昧になる。PM がいないプロジェクトでは誰も Issue を整理しないので、いつまでも漠然とした塊が残る。かといって Issue を開くたびに手動で受け入れ基準を書く習慣は続かない。

### 1 週間で作るならこれ
- `issues: [opened, reopened]` をトリガーに GitHub Actions Workflow が起動
- Issue のタイトル + ボディを Claude API（Haiku）に送信
- レスポンスとして「受け入れ基準（チェックリスト 3〜5 条件）」「実装ステップ（箇条書き 5 項目）」「工数目安（S/M/L とその根拠）」をコメントとして自動投稿
- `breakdown: auto` ラベルがついた Issue のみ動作（誤爆防止、他の Issue には無干渉）
- リポジトリの Secrets に `ANTHROPIC_API_KEY` を設定するだけで導入完了

### なぜ雑か
プロジェクトのコードベースや既存 Issue を読まないため「何番の PR と関連する」といった文脈は無視。日本語の Issue に対しても英語混じりの回答になることがある。コメントの再生成や修正 UI なし（Issue をクローズして再オープンすれば再実行）。rate limit に引っかかったときのリトライなし。

### 雑な技術スタック候補
GitHub Actions YAML + github-script + curl (Claude API) + GITHUB_TOKEN (コメント投稿)

## 3. TokenSync

- カテゴリ: その他 (Figma Plugin)
- 対象ユーザー: デザインシステムを運用するフロントエンドエンジニア・デザイン実装担当者
- 一行で: Figma の Styles を CSS 変数ファイルに変換してワンクリックで書き出す

### 解決する痛み
デザイナーが Figma でボタンの色を `#3B82F6` から `#2563EB` に変更したとき、エンジニアは Figma を開いて値をコピーし CSS ファイルを手動更新する。「あのコンポーネントの色、変わってる?」を毎回確認しに行くのが煩雑。Figma の Dev Mode は有料。`style-dictionary` や `figma-tokens` は設定ファイルの準備に半日かかる。「Figma を開いてボタン 1 回で CSS ファイルを書き出す」だけでいい。

### 1 週間で作るならこれ
- Figma Plugin として起動し、現在開いているファイルの Local Styles（色・テキスト・エフェクト）を自動で列挙
- 色スタイル → `--color-primary: #3B82F6;`、テキストスタイル → `--font-size-heading: 24px;` 形式に変換
- 変換プレビューをプラグイン UI 内で表示（検索・フィルタ付き）
- 「CSS 変数をコピー」でクリップボードに全変数をコピー
- 「.css ファイルをダウンロード」で `tokens.css` として書き出し

### なぜ雑か
グラデーション・画像塗りの色は非対応（Solid のみ）。コンポーネントの Variant ごとのスタイル抽出なし。フォントウェイト・行間など一部テキストプロパティは拾えないケースあり。チームライブラリの External Styles は読めないこともある（Figma API の制限）。命名規則のカスタマイズは MVP では固定フォーマットのみ。

### 雑な技術スタック候補
Figma Plugin API (TypeScript) + Vite (Plugin ビルド) + vanilla CSS (Plugin UI) → Figma Community で公開
