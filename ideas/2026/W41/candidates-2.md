## 1. 片道マイグレーション検知官

- カテゴリ: CLI
- 対象ユーザー: 複数人でDBマイグレーションをレビューしているバックエンド開発チーム
- 一行で: マイグレーションファイルを渡すだけでロールバックできない変更だけを一覧にしてくれるのだ

### 解決する痛み

PRレビューで `DROP COLUMN` や `NOT NULL` 制約の追加のようなマイグレーションが誰にも気づかれずマージされ、本番で問題が起きて「よし戻そう」と思った瞬間に詰む、という場面がある。down migrationファイルは存在していても、実際には元のデータが失われていて戻せないケースも多い。レビュアーはSQLを1行ずつ読んで危険性を判断するほどの余裕がなく、結局「動いたから良し」でマージされていく。

### 1 週間で作るならこれ

- マイグレーションファイル(またはディレクトリ)をCLI引数で渡す
- `DROP TABLE` / `DROP COLUMN` / `RENAME COLUMN` / `NOT NULL`追加 / 型変更 などの危険パターンを正規表現で検出
- 危険度ランキングでファイル名・行番号・理由を一覧表示
- down migrationの有無を突き合わせて「downはあるが実は戻せない」ケースにも警告マークを付与
- `--fail-on-danger` フラグでCIを落とせるexit code対応

### なぜ雑か

対応するマイグレーションツールはRails/ActiveRecord、Prisma、Django、Knexなど色々あるが、最初はSQLファイルの生テキスト解析のみでツール固有DSLのパースは捨てる。実際にDBへ接続してデータ量から危険度を判定する機能はなし(静的解析のみ)。1ファイルに複数操作が混在する場合の精密な行特定も雑に済ませる。

### 雑な技術スタック候補

Node.js + Commander.js + 正規表現パーサ + chalk (色付き出力) + GitHub Actions組み込み用exit code

## 2. 植物日照不足番人

- カテゴリ: ハードウェア
- 対象ユーザー: 観葉植物を育てているが置き場所の日当たりが十分か分からない人
- 一行で: 鉢に置くだけで植物が1日に浴びた光の量が足りているか夜にLINEで教えてくれるのだ

### 解決する痛み

観葉植物が徐々に元気をなくす原因は大抵「水やり」より「置き場所の光量不足」なのに、人間の目では「明るい部屋」と「植物にとって十分な光」の区別がつかない。カーテン越しの窓際に置いたつもりでも実際のlux値は想像よりずっと低いことが多く、気づくのは葉が黄色くなってからで手遅れになる。センサーが1日分の光を数字にしてくれれば、置き場所を変えるかどうかの判断ができる。

### 1 週間で作るならこれ

- ESP32 + フォトレジスタ(光センサー)を鉢の近くに設置
- 1分おきにlux相当値を記録し、日の出〜日没の間で「植物が必要とする明るさ」を超えていた累積分数を計算
- 植物種類は「観葉植物標準(明るい日陰〜半日陰)」の1プリセットのみで固定閾値判定
- 夜21時に累積時間が閾値未満ならLINEで「今日は日照不足かも」を通知
- `http://hikari.local/` で直近7日間の光量グラフを簡易表示

### なぜ雑か

植物種類ごとの必要光量の違いは無視して1種類の閾値で全部判定する。色温度やスペクトルは見ず単純な明るさのみを使う。複数の鉢を同時監視する機能は作らず1台1鉢固定。電源はUSB給電前提でバッテリー駆動は考えない。

### 雑な技術スタック候補

ESP32 + フォトレジスタ + ArduinoJson + LINE Messaging API + LittleFS (ログ保存) + Chart.js (簡易グラフ表示)

## 3. ウィキ風化パトロール隊

- カテゴリ: Bot (Slack)
- 対象ユーザー: Notionで社内ドキュメントを運用しているチームの情報システム・PMO担当
- 一行で: Notionのページ一覧を繋ぐだけで長期間更新されていないページの最終編集者にそっと確認を促してくれるのだ

### 解決する痛み

社内Wikiには「オンボーディング手順」「〇〇の申請フロー」のようなページが山ほどあるが、担当者が変わったり仕組みが変わったりしても誰も更新せず、半年後に新人がその通りにやって詰まる、という場面が繰り返される。古い情報かどうかはページを開いて中身を読むまで分からず、全ページを定期的に見直す余裕は誰にもない。最終更新日はNotion側に記録されているのに、誰もそれを見に行かない。

### 1 週間で作るならこれ

- Notion APIでワークスペース内の全ページの最終更新日・最終編集者を取得
- 180日(可変)以上更新がないページを一覧化
- 該当ページごとに最終編集者へSlack DMで「このページ、まだ合ってますか？」とページリンク付きで送信
- DM内の「OK(まだ合ってる)」「古い」ボタン(Slack Block Kit)で返信を記録
- 週1回まとめて実行するcronジョブ

### なぜ雑か

Confluenceなど他のWikiツールへの対応はなくNotion専用。ページの中身を読んで本当に古いかどうかをAIが判定する機能はなく、更新日だけで雑に判定する。「古い」と返信されたページの修正フローは作らず通知して終わり。子ページやデータベース内のレコードは対象外でトップレベルページのみ扱う。

### 雑な技術スタック候補

Notion API + Node.js + node-cron + Slack Bolt (DM + Block Kit) + GitHub Actions scheduled workflow
