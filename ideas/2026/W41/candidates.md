## 1. 保証切れ速報

- カテゴリ: モバイル (PWA)
- 対象ユーザー: 家電やガジェットをよく買う一人暮らし・新居準備中の人
- 一行で: 保証書やレシートを撮るだけで保証期限が近づくとプッシュ通知で教えてくれるのだ

### 解決する痛み

家電を買うと保証書やレシートをレシート入れや引き出しに適当に突っ込んで、1年後に壊れた時には期限が何日前に切れたかわからず有料修理になる。既存の家計簿アプリはレシートを撮っても「支出額の記録」が目的で保証期限は追わない。手動でカレンダーに入れる人もいるが機種ごとに保証期間がバラバラ(1年/2年/5年など)で入力が面倒で続かない。直接の代替は「レシートを捨てずに保管して自分で覚えておく」か自作のExcel管理表だが、どちらも始めるコストが高くて誰も続けない。

### 1 週間で作るならこれ

- 単一コアフロー: 写真を撮る → OCRで店名・購入日を抽出 → 保証期間(デフォルト1年、手動で上書き可)を設定 → 期限14日前にプッシュ通知、の一本道だけ作る
- レシート/保証書をカメラで撮影してアップロード
- OCR (Google Vision API) で購入日・店名・金額を自動抽出、商品名と保証期間はユーザーが手入力で確定
- 保証期限が近づく14日前と前日にプッシュ通知 (Web Push)
- 登録済みアイテムをカード一覧で表示、タップで元画像を確認
- デモはサンプルレシート画像3枚を同梱し、アップロード→期限通知が立つまでを30秒で触れる合成デモにする(実レシートなしで価値を見せる)

### なぜ雑か

OCR誤読の訂正UIは作らない(手入力で上書きするだけ)。保証期間のカテゴリ別デフォルト値は数種類だけ用意して残りは全部「1年」にする。保証書の原本保管・紛失対応は考えない(写真が残るだけで安心する用途止まり)。複数端末同期は後回しでブラウザのlocalStorageのみ。配布先として家電好きが集まるSNS/コミュニティを想定しているが、実際にそこで触ってもらえるかは検証していない未解決の課題。

### 雑な技術スタック候補

Next.js PWA + Google Cloud Vision API (OCR) + Web Push API + Supabase (DB) + Vercel

## 2. トライアル逃げ切り番

- カテゴリ: Browser Extension
- 対象ユーザー: 無料トライアルに登録しがちだが解約を忘れて課金されるサブスク貧乏な人
- 一行で: 無料トライアル登録を検知するだけで解約期限前にブラウザ通知してくれるのだ

### 解決する痛み

「まず無料で試せます」に釣られてクレカ情報を入れた瞬間、2週間後や1ヶ月後に自動課金されることを忘れる。カレンダーに手動で入れる人もいるが、登録のたびにアプリを開いてリマインダーを設定するのが面倒で結局やらない。既存のサブスク管理アプリ(マネーフォワードなど)はクレカの請求が実際に発生した後に気づく仕組みで、解約期限前には教えてくれない。直接の代替は「請求が来てから気づいて渋々払う」か「手動でGoogleカレンダーに毎回入れる」のどちらかで、どちらも抜け漏れが起きる。

### 1 週間で作るならこれ

- 単一コアフロー: ページ内の「無料トライアル/free trial」等のキーワードを検知 → ポップアップで「トライアル期間は何日?」と1問だけ聞く → 期限を逆算してブラウザ通知を予約、の一本道だけ作る
- 対象ページのテキストに「無料トライアル」「free trial」「◯日間無料」等のパターンがあれば拡張アイコンをバッジ表示
- クリックすると「トライアル期間(日数)」を1つ選ぶだけの簡易フォームを表示
- 入力後、期限の2日前にChrome通知 (chrome.notifications API) で「◯◯のトライアルがもうすぐ終わります」と表示
- 登録済み一覧をポップアップ内にシンプルなリストで表示、不要なものはワンタップ削除
- デモはキーワード検知が効く架空のダミー料金ページ(自作HTML)を1枚用意し、ページを開く→バッジ表示→期限登録までを30秒で見せる合成デモにする

### なぜ雑か

キーワード検知の精度は作り込まず、誤検知(無関係な「無料」表記にも反応)はユーザーが手動で無視すればいいとする。実際の課金日をサイトから自動取得はしない(自己申告の日数ベース)。通知を見逃したら終わり、スヌーズ機能は作らない。対応ブラウザはChromeのみ。配布先はChromeウェブストアが前提になるが、審査期間やストア内で見つけてもらえるかは検証していない未解決の課題。

### 雑な技術スタック候補

Chrome Extension (Manifest V3) + chrome.notifications API + chrome.storage.local (同期なし)

## 3. 当番ローテーションくん

- カテゴリ: Bot (Slack)
- 対象ユーザー: スタンドアップ司会・オンコール・観葉植物の水やりなど交代制の当番がある小規模チーム
- 一行で: メンバーリストを登録するだけで今日の当番をSlackに自動投稿して交代申請も1コマンドで受け付けてくれるのだ

### 解決する痛み

当番制の仕事(スタンドアップ司会、オンコール、ゴミ出し、観葉植物の水やり)は最初はスプレッドシートやカレンダーで管理するが、誰かが休むたびにDMで「代わってもらえる?」とやり取りして、その交代がスプレッドシートに反映されずに次の人が「今日は自分の番だっけ?」と毎回確認する羽目になる。既存のシフト管理SaaSは本格的な勤怠向けで当番表1つ作るには重すぎる。直接の代替は「手動で表を更新し続ける」か「毎回Slackで聞く」で、どちらも更新漏れが起きてローテーションが崩壊する。

### 1 週間で作るならこれ

- 単一コアフロー: メンバーをリスト登録 → 毎朝順番通りに「今日の当番は@田中です」と投稿 → `/duty swap @佐藤` で当日だけ交代申請、の一本道だけ作る
- `/duty add @user` でローテーションメンバーを順番に登録
- 毎朝9時にcronで次の当番を計算してチャンネルに自動投稿(単純な順番繰り上げ、固定ローテーションのみ)
- `/duty swap @someone` で「今日だけ」他の人に交代、ローテーション自体の順番は変えない
- `/duty today` で今日の当番を即確認できるコマンド
- デモは4人のダミーメンバーでローテーションを回し、登録→当番投稿→交代コマンドまでを30秒で見せるSlackワークスペースの合成デモ(スクリーン録画)で示す

### なぜ雑か

複数の当番種別(スタンドアップ司会とオンコールを別管理)には対応せず、1チーム1ローテーションだけ。休暇申請との連携はなし(交代は毎回手動で`/swap`する必要がある)。通知を見逃した場合のエスカレーションはなし。タイムゾーンはチーム全体で1つ固定。配布先はSlack App Directoryへの申請が前提になるが、審査通過までの期間や個人開発アプリがどれだけ見つけてもらえるかは検証していない未解決の課題。

### 雑な技術スタック候補

Slack Bolt (Node.js) + node-cron + SQLite + Railway/Render 無料枠でホスト
