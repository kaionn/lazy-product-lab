## 1. 幽霊チケット発見くん

- カテゴリ: CLI
- 対象ユーザー: スクラムマスターやテックリードで、チケット管理ツール(Jira/Linear)とGitの実態のズレに気づかずスプリントレビューで気まずくなる人
- 一行で: チケット一覧CSVとgit logを渡すだけで「進行中のままコミットが止まってるチケット」と「Doneなのに後からコミットされてるチケット」を教えてくれるのだ

### 解決する痛み

スプリントレビューで「このチケットまだIn Progressだけど最後のコミットいつでしたっけ」と聞かれて初めて気づく。逆に「Doneにしたのに後から直すコミットが生えてる」も誰も気づかず放置される。JiraやLinearのステータスは手動更新なので現実とズレていくが、定期的に目視チェックする人はいない。チケットが30個を超えると人間の目では追えなくなり、気まずい沈黙が生まれる。

### 1 週間で作るならこれ

- チケットID一覧CSV（ID, タイトル, ステータス, 最終更新日）をエクスポートして渡す
- `git log --all` からコミットメッセージ内のチケットID（例: PROJ-123）を正規表現で抽出
- チケットごとに「最後に紐づいたコミット日時」を集計
- ステータスが In Progress/In Review なのに直近14日コミットなし → 「停滞」としてランキング表示
- ステータスが Done なのに直近3日以内にコミットがある → 「蒸し返し」として別リストで警告

### なぜ雑か

コミットメッセージにチケットIDが書かれていない場合は検出不能（規約を守っているチーム前提）。ブランチ名からの抽出は対応しない。Jira/LinearへのAPI直結はせずCSVエクスポート前提なので毎回手動作業が必要。複数リポジトリをまたぐチケットは非対応。直接代替は「スプリントレビューで一つずつ口頭確認する」か「JiraのSLAダッシュボードを目視で見る」で、どちらも見落としが起きやすい点がこの案の立ち位置。合成デモは架空のチケットCSV20件とダミーgit logを用意すれば「停滞3件・蒸し返し1件」を30秒で表示できるはず。配布先は社内Slackの開発者コミュニティを想定しているが、実際に興味を持つチームがいるか、GitHub上で検索需要があるかは未検証の仮説。

### 雑な技術スタック候補

Python + GitPython + pandas + Rich（ターミナル表示） + 正規表現

## 2. 二重買い報告くん

- カテゴリ: Bot (LINE)
- 対象ユーザー: 家族や同居人と日用品のストックを共有しているが、それぞれ別々に買い物してしまう人
- 一行で: 買ったものをLINEに一言送るだけで同じものを最近他の家族も買っていたら教えてくれるのだ

### 解決する痛み

「トイレットペーパー買っておいたよ」と言う前にもう一人が買ってきていて、気づいたら同じものが3パックも積んである。買い物リストアプリを共有しても結局見ずに買う。LINEグループで「買った」と報告する習慣はあっても、過去の報告を遡って確認する人はいない。チャット履歴に埋もれて誰も気づかず、同じ失敗が月に何度も起きる。

### 1 週間で作るならこれ

- LINE公式アカウントを家族グループに追加し、各メンバーが「○○買った」とテキストで送るだけ
- 固定辞書（洗剤・トイレットペーパー・ティッシュなど20品目限定）で商品名キーワードを文字列マッチで抽出
- 直近14日以内に同じ商品名の報告が既にあれば「〇〇さんが3日前に買ってるよ」と即リプライ
- 辞書にない商品名もログだけ保存（重複チェックはスキップ）
- 週1回グループに「今週買われたものリスト」をまとめて送る

### なぜ雑か

商品名のゆらぎ（「トイレペーパー」「トイペ」）は固定辞書に登録したものしか拾えない。数量や個数は無視して「買った/買ってない」の二値のみ判定する。既存の買い物共有アプリ（Bring!やOurGroceries）という直接代替があるが、それらは「買う前にリストに追加する」運用を要求する点が、今回の「買った後にLINEで一言言うだけ」より手間がかかるという差別化のつもり。合成デモは20品目のダミー発言ログを用意し、2人目が「ティッシュ買った」と送った瞬間に重複警告が返る様子を30秒で見せられる。配布先は家族向けよりも先に小規模オフィスの備品共有で需要を試す方が到達しやすいかもしれないが、これは検証していない仮説。

### 雑な技術スタック候補

LINE Messaging API + Node.js (Express webhook) + SQLite + 固定キーワード辞書（文字列includes判定、形態素解析は使わない）

## 3. クール便放置番

- カテゴリ: ハードウェア
- 対象ユーザー: 在宅率が低く、冷蔵・冷凍の宅配を置き配指定していることが多い一人暮らし
- 一行で: 玄関前に置くだけで冷蔵/冷凍便が届いてから気づかず放置されていたらLINEで教えてくれるのだ

### 解決する痛み

クール便を置き配指定しているが、仕事中で気づかず3時間後に帰宅して冷凍食品が半分解けていたことがある。宅配ボックスは満杯検知はあっても「中身が傷みそうな速度で放置されている」ことまでは教えてくれない。何時に届いたかもインターホンの履歴を遡らないとわからず、気づいた頃には手遅れになっている。

### 1 週間で作るならこれ

- 振動センサーと温度センサーを積んだ小型デバイスを玄関マットや置き配指定場所の近くに設置
- 振動検知（ドンと置かれた衝撃）をトリガーに「荷物到着」とタイムスタンプを記録
- 到着後、周辺気温が一定以上（例: 25度超）なら放置リスクを「高」判定
- 到着から60分経過しても玄関ドアの開閉（別の磁気センサー）が検知されなければLINEで「荷物が60分放置されてるよ、傷むかも」と通知
- 設定はWi-Fi接続とLINE Notify連携のみ、しきい値（60分/25度）は固定でUIは作らない

### なぜ雑か

振動検知は宅配以外の物音（風で物が落ちた等）でも誤反応する前提で割り切る。クール便かどうかの判別は一切できず、すべての置き配を同じ扱いにする。複数箇所に荷物が置かれるケースは1箇所しか監視できない。直接代替は「置き配をやめて対面受け取りにする」か「宅配ボックスを使う」だが、どちらも在宅の工夫や設置コストが要るのに対し、後付けセンサーで済ませる雑さがこの案の価値。合成デモは段ボール程度の重さを振動センサーにぶつけて到着を記録し、60分相当を早送りしたタイマーで通知が来る様子を30秒のスクリーン録画で見せられる想定。配布先は一人暮らし向けガジェットのニッチだが、クール便トラブルで実際に困っている母数がどれくらいいるかは未検証の仮説。

### 雑な技術スタック候補

ESP32 + 振動センサー(SW-420) + DHT22（温湿度） + リードスイッチ（ドア開閉） + LINE Notify API + Arduino IDE
